# ARBITER — §4.2 inputs: what is missing, and the wall in the way

**Status: scope, recorded 2026-08-10. Not a design. Written because the redesign §9 says
"the redesign is worthless without the new inputs" and none of them exist, and because
scoping the work surfaced a conflict between §4.2 and §4.3 that has to be settled before
anyone builds it.**

---

## 1. What is missing, measured

§4.2 names five new inputs. §5.4 names six new rule categories for the v2.0 seed set.
**Neither exists.**

| | state, verified 2026-08-10 |
|---|---|
| `EvidenceClaim` (`packages/engine/src/types.ts:38`) | Carries exactly six discriminating fields — `stream`, `system`, `measuresKeyEvent`, `exposureRelevant`, `inApplicabilityDomain`, `klimisch` — one per rule R6, R1, R2, R3, R4, R5. **No field for dose, logP, injury pattern, reversibility or frequency.** |
| `rules/ruleset-v2.0.json` | **R1–R6 only.** §5.4's six new categories — dose magnitude, injury pattern, reversibility and adaptation, expected frequency, reactive-metabolite formation, latency and dechallenge — are absent. The v2.0 re-registration corrected the *target* (§4.1), not the rulebook. |
| `data/out/tak994.json` | Claims carry the six engine fields and nothing else. |

So the configuration currently under measurement is **the v1.0 six rules over six thin
fields** — which is the configuration §0 measured as producing five over-calls, and which
§9's *fluent wrongness* row says an AI will reproduce "but persuasively."

---

## 2. The conflict that has to be settled first

**Three of §4.2's five inputs are sourced from LiverTox. §4.3 forbids LiverTox as an
input.**

| §4.2 input | §4.2's stated source | safe as an input? |
|---|---|---|
| Daily dose | FDA labels / DailyMed | **yes** |
| Lipophilicity (logP) | public chemistry databases | **yes** |
| Injury pattern | **LiverTox** | **no — §4.3** |
| Reversibility / adaptation | **LiverTox** | **no — §4.3** |
| Expected frequency | **LiverTox likelihood score** | **no — §4.3** |

§4.3 is unambiguous and is marked non-negotiable:

> "LiverTox is a label source and must never reach the model as an input. An AI that
> reads a LiverTox monograph and then predicts that drug's hepatotoxicity has read the
> answer. It would score near-perfectly and mean nothing."

and its enforcement — *"a test asserts no label-derived field appears in any adjudication
payload"* — would **block three of the five inputs by construction**.

The chapter-split design (§4.4) does not rescue them either: injury pattern,
reversibility and observed frequency are what the **clinical** chapter reports, and the
clinical chapter is the answer key. §10 #14 forbids it reaching the model.

### The shape of the resolution

The three blocked fields are legitimate **product** inputs and illegitimate **benchmark**
inputs, and the difference is whether a label exists:

- **A novel compound has no LiverTox monograph.** A sponsor's own study report may state
  injury pattern and reversibility from animal data, and that is evidence, not an answer.
- **A historical compound has a monograph, and it is the answer.** Populating those
  fields there is leakage however it is routed.

So §4.2's table is describing the product case, and §4.3 is describing the benchmark
case, and the document does not say so. **That distinction needs writing into §4.2
before the fields are built**, or the first person to implement it will populate all five
from LiverTox because §4.2 tells them to, and §4.3's test will either fail or — worse —
not exist yet to fail.

**Note:** `test_qsar_leakage.py`, cited by §4.3 as the ancestor its enforcement descends
from, is **not present in this repository** at the paths the specs reference. Leakage
checks exist in `data/prep/tests/test_splits.py`. Whatever §4.3's test descends from,
that ancestry should be corrected or the file restored before it is relied on.

## 3. Where the inputs can land safely today

**Gate 0's probe case.** `data/out/tak994.json` records
`excludedFromBenchmark: true` — *"Terminated in Phase 2 and never approved, so absent
from DILIrank. It is the motivating case, not evidence."*

There is no answer key for TAK-994 and the flip rate needs none, so **the leakage wall
does not bind on the consistency probe.** All five §4.2 fields can be added to the probe
case without any §4.3 exposure.

That makes the cheap first move available: extend `EvidenceClaim` and the probe case with
the five fields, populate them for TAK-994 from its public record, and re-measure the
flip rate against a case that actually carries severity information. It tests §9's
*fluent wrongness* claim directly and it costs no benchmark integrity.

---

## 4. What this document does not do

**It does not supply values.** Daily dose, logP, injury pattern, reversibility and
expected frequency for TAK-994 are toxicological facts with sources, and inventing them
would be the same defect as a fabricated flip rate — worse, because they would be
laundered through the engine and signed. Each needs a cited source and, per §4.4a's
discipline, a human who read it.

**It does not amend §4.2 or §4.3.** The conflict in §2 is stated so it can be settled by
whoever owns the spec; it is not settled here.

---

## 5. Order, if this is picked up

1. Settle §2 — amend §4.2 to distinguish product inputs from benchmark inputs, or
   restrict it to dose and logP.
2. Correct or restore §4.3's cited ancestor, and write the payload test **before** any
   label-derived field exists to leak.
3. Extend `EvidenceClaim` + the probe-case generator with the five fields (leakage-free
   on TAK-994, §3 above).
4. Populate TAK-994 from cited public sources, with a manifest per §4.4a.
5. Add §5.4's rule categories to a **v2.1** ruleset — not an edit to v2.0, per §10 #1.
6. Re-run Gate 0. The flip rate on a case carrying severity information is the number
   that tests whether the redesign's premise holds.
