## 2. `rules/evidence-checklist-v1.0.json` item structure

File is 130 lines. Top level: `_note` (1 line), `_whyTwoHalves`, `version: "1.0"` (line 4), `items` (lines 5-126, 12 entries), `_whyAppliesTo` (line 127), `_whyNotApplicableText` (line 128).

Item schema, enforced by `isChecklist` at `services/api/inventory.ts:212-236`:

```ts
interface ChecklistItem {          // services/api/inventory.ts:27-45
  id: string;                      // unique; duplicates make isChecklist return false
  half: "mechanism" | "consequence";
  field: string;                   // the question, in the reviewer's words
  whatItBlocks: string;            // what goes wrong when it is unanswered
  appliesTo?: Modality[];          // omitted = applies to everything
  whyNotApplicable?: string;       // rendered INSTEAD OF whatItBlocks when n/a
}
```

The twelve items, exactly:

| id | half | field | `appliesTo` | has `whyNotApplicable` |
|---|---|---|---|---|
| M1 | mechanism | Human-cell hepatotoxicity result | small_molecule, biologic | no |
| M2 | mechanism | Bile-salt export pump / hepatobiliary transporter inhibition | small_molecule | yes |
| M3 | mechanism | Reactive metabolite or covalent binding assessment | small_molecule | yes |
| M4 | mechanism | Mitochondrial toxicity result | small_molecule | yes |
| M5 | mechanism | Repeat-dose in vivo liver findings | small_molecule, biologic | no |
| M6 | mechanism | Structural alert or QSAR assessment, with applicability domain stated | small_molecule | yes |
| C1 | consequence | Projected human daily dose | both | no |
| C2 | consequence | Exposure margin: tested concentration or NOAEL against projected human Cmax | both | no |
| C3 | consequence | Injury pattern: hepatocellular, cholestatic or mixed | both | no |
| C4 | consequence | Reversibility on withdrawal | both | no |
| C5 | consequence | Expected frequency and the population that would be exposed | both | no |
| C6 | consequence | Intended dosing duration | both | no |

`buildInventory` (`services/api/inventory.ts:130-189`) resolves each item to exactly one of four states, and the order of the checks is load-bearing:

1. `!applies` -> `not_applicable`, **checked before coverage** (comment at lines 155-157: a stray `covers` entry must not silently reinstate a question that does not arise).
2. `covering.length === 0` -> `absent`.
3. `covering.every(f => f.assertion === "ambiguous")` -> `inconclusive`.
4. otherwise -> `present`.

`findingIds` is `.sort()`ed (line 177) because the inventory is hashed into the deliberation log and load order must not move the hash. Entries are sorted by `itemId` (line 181) and by nothing else. `unmappedFindingIds` (line 187) collects any finding declaring a `covers` id the checklist does not contain.

`absentForAdjudication` (lines 200-210) is the join to the model: it drops `present` and `not_applicable`, and renames an inconclusive field to `"<field> (tested, inconclusive)"`.

**Coverage is declared, never inferred** (header comment lines 106-121). There is no keyword matching anywhere.

## 3. The four human manifests: the extraction scoring key

### 3.1 The finding schema, as it actually appears on disk

All three `data/cases/*.json` files use identical finding keys. Measured union across all three:

```
{ id, label, assertion, detail, sourceDocument, sourcePage, covers }
```

`data/probe-case.json` findings carry only `{ id, label, assertion, detail }`; their `covers` lives in the separate `data/probe-case-coverage.json` and is joined at `services/api/cases.ts:148`.

Types those fields must satisfy:

- `assertion` is `"toxic" | "safe" | "ambiguous"` (`services/api/adjudicate.ts:44`, mirroring `packages/engine/src/types.ts:2`).
- `Finding` is declared at `services/api/adjudicate.ts:46-53` with `sourceDocument?: string` and `sourcePage?: number` optional.
- `CoveringFinding extends Finding` at `services/api/inventory.ts:122-128`, adding `covers?: string[]` and `sourceDocumentId?: string`.

Case-file envelope, as loaded by `CaseFile` at `services/api/cases.ts:96-104`:

```ts
interface CaseFile {
  caseId: string;
  compoundLabel: string;
  context: string;
  modality: Modality;               // "small_molecule" | "biologic"
  findings: CoveringFinding[];
  documentScope?: string;           // no default text; present only where true
  _source: { document: string; chapterUsed: string };

```

Underscore-prefixed keys (`_note`, `_source`, `_extractedBy`, `_whyThisCompound`, `_honestLimit`, `_onTheScopeNote`, `_whyOnlySevenOfTwelve`, `_THIS_CASE_IS_NOT_A_BLIND_PREDICTION_TEST`, `_onTheTwoPageChapter`) are documentation. ### 6.1 Templating

`userPrompt(req, template)` at `services/api/adjudicate.ts:173-200`. The template array is `.join("\n")`ed then five `String.prototype.replace` calls run, **each replacing only the first occurrence**:

```ts
return template.join("\n")
  .replace("{{compoundLabel}}", req.compoundLabel)
  .replace("{{context}}", req.context.trim() === "" ? "(none supplied)" : req.context)
  .replace("{{rules}}", rules)

```

The three list placeholders are pre-rendered in the same function:

- `rules` (lines 174-176): `"${id} (${name}), ${enabled ? "enabled" : "disabled"}, strength ${strength}: ${statement}"` per line.
- `findings` (lines 178-187): `"${id} | ${label} | asserts: ${assertion} | ${detail}${src}"` where `src` is `" [source: ${sourceDocument} p.${sourcePage}]"` when present. Empty list renders `"(none)"`.

The system prompt is `prompt.system.join("\n")` at `services/api/adjudicate.ts:278` and `services/api/probe.ts:93`.

### 6.2 Hashing

`promptHash` at `services/api/probe.ts:45-49`:

```ts
export function promptHash(prompt: { system: string[]; userTemplate: string[] }): string {
  return createHash("sha256")
    .update(JSON.stringify({ system: prompt.system, userTemplate: prompt.userTemplate }))
    .digest("hex");
}
```

Facts a prompt author must not get wrong:

- It hashes **only** `system` and `userTemplate`. `version`, `registeredAt`, `purpose`, `registrationNote` and `decoding` are outside the hashed surface. Changing `decoding.temperature` therefore does **not** move the hash.
- It uses plain `JSON.stringify` of a two-key object literal, **not** `canonicalJson` from `apps/harness/src/preregistration.ts:17-22`. Key order is fixed by the literal, so it is stable in practice, but it is a different mechanism from the ruleset hash and the two must not be conflated.
- No pre-registered constant for this hash exists anywhere. There is no `PRE_REGISTERED_PROMPT_HASH`. The hash is recorded into `ProbeOutput.promptHash` (`services/api/probe.ts:38-42, 117`) and printed by `apps/harness/src/consistency-report.ts:39`, but nothing compares it to a committed value the way `load.ts:50` compares the ruleset hash.

### 8.2 The upload ladder (`DocumentStore.upload`, lines 114-152)

1. **Size** (115-117). `MAX_BYTES = 80 * 1024 * 1024` (line 63). Comment: the largest review collected is 8.5 MB, so this is headroom, not an opinion about documents.
2. **Magic bytes** (118-120). `looksLikePdf` (67-69) checks `bytes.subarray(0,5).toString("latin1") === "%PDF-"`. Comment at 65-66: "An extension is a claim by the uploader; the header is a property of the file."

4. **Write, then measure** (131-141). The file is written to `<root>/<id>.pdf` before measurement, and on refusal it is **kept on disk** (comment 137-139) so the reason can be rechecked and an OCR pass run against the exact bytes rejected.

### 9.3 Concrete facts a scorer would have to settle first

1. **Which text does the extractor read?** The manifests were written by hand from `data/out/reviews/<stem>.nonclinical.txt`. That file is not in the checkout. Reproducing it needs the PDF plus `split_review.py` plus PyMuPDF.
2. **What counts as a match?** The manifests are 4, 8 and 9 findings with hand-written `id`s (`TUR:liver-histopathology`) that no model would reproduce. Matching must be on content, and the only mechanically comparable fields are `assertion`, `sourcePage` and `covers`. `detail` is a verbatim quotation plus editorial commentary in the same string - see `IMA:albumin-cholesterol` (line 79), whose `detail` ends "Covers no checklist question: it is neither a liver-injury finding nor an answer to one."
3. **`sourcePage` conventions differ between manifests** (§3.6). Turalio's pages sit outside its own declared chapter range.
4. **Two findings on one topic is correct on nipocalimab**, not a duplicate (§3.3). A scorer that de-duplicates by topic would score the correct behaviour as a hallucination.
5. **`covers: []` is a real answer, used 8 times across the four manifests** (3 in nipocalimab, 3 in slynd, 2 in turalio, 1 in probe-case-coverage). Each has a written reason. Scoring coverage as a set-similarity metric over non-empty sets would silently drop the case that `data/probe-case-coverage.json:14` argues about at length.
6. **Denominators, per the house rule.** The four manifests total 27 findings (6 + 9 + 4 + 8) across 4 documents, 2 modalities, 2 regulators. Every reported recall figure has to name that n, the per-case split, and the prompt hash (`prompts/adjudicator-v1.0.json` is the adjudication prompt; **an extraction prompt does not exist and would need its own registered, hashed file** - there is no `prompts/extractor-*.json`).
7. **Turalio must not be used to score prediction** (`data/cases/turalio-pexidartinib.json:13`). It is legitimate for extraction scoring, because extraction is a reading task rather than a prediction task, but the finding `TUR:clinical-forward-reference` is itself the leak and an extractor that omits it would be scored as a miss.

## 10. What (b) a leakage screen would actually require

### 10.1 The measured fact it exists to enforce

`data/cases/turalio-pexidartinib.json:13` and HANDOVER §13.4c (lines 1701-1727). The sentence in the **nonclinical** chapter:

> "The liver is a major target organ **clinically**, with frequent elevations in transaminases, including serious ones (refer to Section 8.3 of the review for details)."

HANDOVER 1723-1727: "Any future prediction scoring must **grep the nonclinical extract for clinical cross-references first** and exclude documents that contain them. That check does not exist yet."

`docs/superpowers/specs/2026-08-09-arbiter-completion-plan.md:147-155` (Gate 3a) names the target vocabulary: `clinically`, `refer to Section 8`, `in the clinic`, `in patients`, "transaminase language tied to human data", and states the expected outcome: "Turalio fails this screen; nipocalimab passes."

- `data/prep/split_review.py` is the style model and has the pattern for a refusing screen (§7.3). Guard 2 (lines 211-215) applies exactly these heading patterns to the input pages.
- `data/prep/tests/test_split_review.py` is the test style model (§7.3).
- `data/prep/measure_pdf.py` is the second style model: a term-counting refusal ladder over one text blob, printing JSON to stdout.
- `data/prep/tests/test_qsar_leakage.py` is the naming precedent for a leakage test file, and `test_model_never_saw_calibration_or_test_compounds` is docstringed "The single most important test in the data layer."

### 10.4 Concrete constraints a screen would face, from the data

1. **It cannot be heading-based.** The leaking sentence is body prose mid-chapter. `split_review.py`'s guard 2 already catches heading-level interleaving and did not catch this.
2. **Bare keyword counting will produce false positives on the negative example.** Measured against the manifest text that quotes the nipocalimab extract: `IMA:albumin-cholesterol` (line 79) contains "a similar pattern appears clinically", and `IMA:margin-applicant` (line 43) contains "safety margin of 44x to the **clinical** setting". Both are legitimate nonclinical-chapter usages of a clinical word. The completion plan asserts nipocalimab passes the screen; on a naive `clinically` grep against the manifest quotations it would not. Whether the underlying extract behaves the same cannot be checked from this checkout (§3.5).
3. **The screen has to run before the model, not after.** The only current pre-model gate is `split_review.plan_split`, and it returns a `Split`. Any new screen has the same shape available: pure function over page strings or one text blob, returning a dataclass with `ok`, `reason`, and enough evidence (matched phrase, page index, character offset) that a human can check the call without re-reading the PDF.
4. **The document-level answer is binary but the evidence is per-match.** Turalio's leak is one sentence out of a ~30-page chapter; the refusal reason has to quote it, exactly as `split_review.py`'s refusals quote the failing condition.
5. **Modality/regulator split matters.** `data/cases/nipocalimab-imaavy.json:13` and HANDOVER 1720-1722 both record that EMA assessment reports have the non-clinical section written before and separately from the clinical one, and FDA multi-discipline reviews do not. Any measured pass/fail rate has to name which regulator each document came from; the current n is 2 usable documents (1 FDA, 1 EMA), plus slynd whose chapter reports no studies at all.
